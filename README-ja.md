# Slug-Free Permalinks

English: [README.md](README.md)

公式ページ: [English](https://happas.jp/en/slug-free-permalinks/) | [Japanese](https://happas.jp/slug-free-permalinks/)

変更履歴: [日本語](CHANGELOG.md) | [English](CHANGELOG.en.md)

通常投稿はWordPress標準のパーマリンク設定を使い、カスタム投稿タイプとタクソノミーにIDベースURLを適用するプラグインです。

## なぜこのプラグインが必要か

WordPressのスラッグは便利ですが、日々の運用では地味に面倒なことがあります。

このプラグインは、たとえば次のような悩みがあるサイト向けです。

- 記事を書いたり、カテゴリやタグを増やすたびにスラッグを意識したくない
- 2バイト文字がURLエンコードされて、URLが長く見づらくなるのを避けたい
- 後からタイトルを変更したときに、タイトルとスラッグが食い違うのを防ぎたい

Slug-Free Permalinksは通常投稿のパーマリンクをWordPress標準設定に任せ、選択したカスタム投稿タイプやタクソノミーにIDベースURLを適用します。

このプラグインは、新規サイトや、まだパーマリンク方針を固めている途中のサイト、あるいはスラッグ運用が不要な構造化コンテンツ向けのケースに向いています。

すでに大量の記事を公開していて、スラッグベースURLを広く運用しているサイトでは、導入前に影響をよく確認してください。既存の被リンク、検索流入、SNSシェア、編集フローへの影響を見ておくのが安全です。

## 特徴

- 公開かつUIを持つカスタム投稿タイプを個別に選択
- 公開かつUIを持つタクソノミーを個別に選択
- 選択したタイプに登録されたrewrite slugをIDベースURLにも使用
- カスタム投稿タイプ・タクソノミーのスラッシュ／ハイフン形式を選択
- 必要に応じて旧スラッグURLから現在のIDベースURLへ301リダイレクト
- Polylangが実際に公開している言語ホームURLを基準に言語URLを維持
- 通常投稿のパーマリンクをテンプレートやWordPressタグから1つの編集欄で組み立て、旧方式のID URLも明示的に移行
- オプションで旧CMSの識別子（`legacy_id`）をURLに使用。値がない記事は投稿IDまたはスラッグへフォールバック
- 設定変更時にリライトルールを自動フラッシュ

## 他CMS・ブログサービスからの移行に

旧サービスの記事URLが`/entry/12345.html`で、WordPressでの投稿IDが`987`になった場合でも、インポート時にカスタムフィールド`legacy_id`へ`12345`を保存すれば、WordPressのパーマリンク構造`/entry/%legacy_id%.html`で同じURLパスを使えます。

1. 旧CMSから記事と旧ID（または旧スラッグ）を取り込み、記事の**通常のカスタムフィールド`legacy_id`**に保存します。
2. Slug-Free Permalinksの「移行元の識別子を使用」を有効にします。旧v1形式の通常投稿は先にWordPress標準形式へ移行してください。
3. 通常投稿の構造に`%legacy_id%`を使用します。カスタム投稿タイプは対象を選択すると登録済みのrewrite slugの下で旧識別子を使用します。
4. `legacy_id`のない新規記事は投稿ID（既定）または投稿スラッグへフォールバックします。

`legacy_id`が有効でも、旧スラッグURLからの301リダイレクトをONにしていれば、識別子が競合しない既存のカスタム投稿タイプのスラッグURLを正規URLへ転送します。識別子と別記事の旧スラッグが競合する場合は誤転送を防ぐため404になります。

`legacy_id`の入力欄やインポート機能は追加しません。既存のカスタムフィールドを読むだけです。識別子は英数字・ハイフン・アンダースコアに対応し、異なる記事が同じURLを持つ場合は誤った記事を表示せず404になります。旧URLの維持には同じドメインとパス構造、衝突のない識別子が必要です。移行前にバックアップを取り、URLを検証してください。

## FAQ

**固定ページ（page）にも対応していますか？**

いいえ。固定ページは意図的に対象外にしています。多くのWordPressサイトでは固定ページに固有のURL構造があり、スラッグを外すと競合が起きやすいためです。

通常投稿はWordPress標準のパーマリンク設定で管理し、カスタム投稿タイプとタクソノミーのID URLを補完します。

---

**すべての旧URLをリダイレクトしますか？**

いいえ。すべての404に対してスラッグを推測するような挙動はしていません。

WordPressがすでに対象コンテンツを解決できる場合のみ、旧スラッグURLから現在のIDベースURLへリダイレクトします。

---

**なぜ404ごとにスラッグ検索を行わないのですか？**

すべての404リクエストに対してスラッグ検索を行うと、不要なデータベースクエリが発生しやすく、特にボットアクセスが多い環境では負荷が増える可能性があります。

Slug-Free Permalinksはパフォーマンスと予測可能な挙動を優先した設計になっています。

---

**投稿タイプとタクソノミーのスラッグを同じにできますか？**

いいえ。同じ登録済みrewrite slugを持つ投稿タイプとタクソノミーを同時に選択した場合、設定の保存を拒否します。

異なるrewrite slugを使うことで、IDベースのルート競合を防ぎます。

---

**Polylangや `/en/` のような言語ディレクトリ付きURLでも使えますか？**

はい。Polylang連携では、任意のパスプレフィックスを許可せず、Polylangが返す言語ホームURLを基準にURLとrewrite ruleを構成します。

たとえばPolylangが`/en/`を言語パスとして公開している場合、選択したカスタム投稿タイプや分類の`/en/books/123/`、`/en/category/45/`などのURLに対応します。別ドメイン方式やクエリ方式では、Polylangが返すURLをそのまま利用し、不要なパスプレフィックスは追加しません。

**通常投稿のID URLをWordPress標準設定に移行できますか？**

はい。旧方式で通常投稿を管理している場合、設定画面の「通常投稿」セクションに表示される移行ボタンから、現在のID URL形式をWordPress標準の`%post_id%`構造へ移行できます。通常投稿はプラグインの対象から外れ、カスタム投稿タイプとタクソノミーの選択状態は維持されます。

移行操作はサイト全体のパーマリンク構造を変更します。カスタム投稿タイプなどのURLにも影響する可能性があるため、実行前にバックアップを取り、既存URLやリダイレクトを確認してください。

**プラグインを無効化しても通常投稿のURLを維持できますか？**

通常投稿を対象にしている場合、設定画面には現在のID URL形式と同等のWordPressカスタム構造（`/post/%post_id%/`または`/post-%post_id%/`など）が表示されます。無効化する前に移行ボタンを使ってWordPress標準設定へ切り替えてください。

カスタム投稿タイプとタクソノミーは別途URLの確認が必要です。また、通常投稿の構造に`%legacy_id%`を使用している場合は、無効化すると独自タグのURL生成・解決ができなくなります。無効化前に標準タグへ切り替えるか、旧URLの転送を用意してください。

---

## 動作要件

- WordPress 6.4 以上
- WordPress 7.1 まで動作確認済み
- PHP 8.2 以上

これらを最低対応バージョンとし、それより古い環境はサポート対象外です。

## インストール

1. WordPress管理画面で`Plugins > Add New`を開きます。
2. `Slug-Free Permalinks`を検索します。
3. `Install Now`をクリックし、その後有効化します。
4. 通常投稿はWordPress標準のパーマリンク設定を使い、プラグイン設定ではカスタム投稿タイプ・タクソノミーとID URL形式を選びます。

手動インストールする場合は、`slug-free-permalinks`ディレクトリを`/wp-content/plugins/`に配置してから`Plugins`画面で有効化してください。

## 注意点

- 選択した投稿タイプまたはタクソノミーの登録済み rewrite slug が同じ場合、設定保存を拒否してIDベースのルート競合を防ぎます。
- 接頭辞付きIDルートとして登録するのは、Polylangの言語ホームURLから確認できる実在パスだけです。任意のパス接頭辞は受け付けません。
